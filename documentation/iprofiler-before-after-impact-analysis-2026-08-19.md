# iProfiler — Before vs. After Impact Analysis

**Date:** 2026-08-19
**Source:** Actual git diffs from commits `88613a9` and `5170729` ("Bug Fixes") in the Vaultmind/iProfiler repository.

| Module / Feature | Before Fix (Root Issue & Behavior) | After Fix (System Resolution & Impact) | Primary Benefit |
|---|---|---|---|
| **OCR Service & Docker Execution** (`ocr_service.py`) | Tesseract's executable path was hardcoded to a Windows-only location (`C:\Program Files\Tesseract-OCR\tesseract.exe`), so any Docker/Linux deployment would need a code edit to even find the binary. Worse, when Tesseract failed for any reason, `extract_with_tesseract()` caught the exception and returned the string `"OCR extraction failed: ..."` as if it were real extracted text — that fake text could get saved as a document's `raw_text` and shown to users as genuine content. | The path now comes from an optional `TESSERACT_CMD` env var — unset by default, which lets `pytesseract` resolve the binary via `PATH` automatically inside Docker/Linux (matching how the `tesseract-ocr` package installs there), and only needs setting for local Windows dev. On failure, the function now raises a dedicated `OCRError` instead of returning a string, so a real OCR failure can no longer masquerade as extracted document text. | Environment-portable OCR execution (no more platform-specific hardcoding) and failures fail loudly instead of silently corrupting extracted data. |
| **Qwen Model Extractions** (`qwen_service.py` — `recognize_for_ivault`) | `recognize_for_ivault()` itself wasn't directly rewritten, but every one of its OCR calls goes through `call_qwen_vision()`, which — before the fix — had zero retry handling. A dropped connection or a momentary LM Studio restart mid-recognition meant the whole call failed immediately, and `recognize_for_ivault` would return `None` for every requested iVault property with no second attempt. | Because `call_qwen_vision()` (its only path to the model) is now wrapped in the shared `_call_qwen_with_retry` helper, `recognize_for_ivault`'s calls inherit automatic retry on transient failures without any change to its own logic — a dropped connection during iVault property recognition now retries instead of silently nulling out every property on the first hiccup. | iVault property recognition survives transient backend blips instead of failing outright on the first dropped connection. |
| **API Connection Handling** (`qwen_service.py` — low-level call sites: `call_qwen_vision`, `call_qwen_text`, `call_qwen_messages`) | Each function called `client.chat.completions.create(...)` directly with no error handling at all. Any `APIConnectionError` (including timeouts), `InternalServerError` (5xx), or `RateLimitError` (429) from the LM Studio/Ollama backend propagated immediately as a raw, unhandled exception straight up into whatever pipeline step was running — one bad network moment could kill an entire document's processing. | All three call sites are now routed through a shared `_call_qwen_with_retry(fn, label=...)` wrapper: retries only the genuinely transient error classes (connection/timeout/5xx/rate-limit) up to 3 times with exponential backoff (1s → 2s → 4s), and only after exhausting retries raises a single clean `QwenServiceUnavailableError` — while real 4xx/validation errors still surface immediately, unretried. | Transient backend/network failures no longer crash in-flight document processing; only genuine, persistent outages surface as errors. |

## Overall Stability & Performance Improvement

The pipeline moved from treating every OCR or model-call failure as fatal and, in OCR's case, sometimes silently masking that failure as real data, to a model where transient errors (dropped connections, brief backend restarts, rate limits) are retried automatically and only genuine failures propagate as clearly typed exceptions. Combined with the earlier fixes to upload concurrency and lazy highlight extraction, this makes the document-processing pipeline both more resilient to backend hiccups and less likely to silently corrupt extracted data — a meaningful stability gain on top of the raw speed improvements already measured.
